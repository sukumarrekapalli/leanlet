# Leanlet 0.3.0-beta.1 release notes

Release channel: prerelease (`next`). The public stable line remains 0.2.0.

## Why this release exists

The 0.2 package proved that a compact browser model could ship with an
application. This beta adds the control plane required when an application has
more than one local capability: explicit registration, bounded scheduling,
lifecycle ownership, structured uncertainty, composition, and release
evidence.

## New framework surface

- `LeanletKernel` and `createLeanletKernel` for typed registration, lazy
  loading, reuse, concurrency/deadline/declared-memory budgets, provider and
  network admission, priority ordering, idle eviction, events, and snapshots.
- `defineFlow` for declared dependencies, parallel application orchestration,
  outer deadline/priority propagation, and completion traces.
- `accepted` and `abstained` result constructors plus structured failed results,
  timing, and provenance.
- `planLeanletAssets` for release byte planning, path deduplication, conflict
  detection, and hash requirements.
- `evaluateClassification` for coverage, accuracy, accepted accuracy, macro F1,
  per-label metrics, and p50/p95 latency.

## Performance work

In-flight request coalescing allows concurrent requests with the same Leanlet ID
and application key to share one queued or active computation. Callers retain
independent cancellation. The included synthetic benchmark runs 24 identical
requests as one execution; it is a scheduler sanity check, not a device or model
performance claim.

## Reliability and compatibility

- The 0.2 `defineLeanlet` path remains first-class and requires no kernel.
- `VisionLeanlet` propagates worker crashes, supports per-request cancellation,
  rejects use after destroy, and exposes a `cancelled` event.
- `CategoryResult.score` replaces misleading confidence terminology;
  `confidence` remains as a deprecated compatibility alias.
- Kernel options and manifests receive runtime validation.
- Simultaneous first runs share loading.
- Shutdown clears registered state even if disposal reports a failure.
- Asset installation verifies pinned files before replacing local copies.

## Reference application and documentation

SafeShare is a working browser-only reference product built from eight actual
Leanlets: secret detection, personal-data detection, URL inspection, language,
tone, readability, deterministic redaction, and release policy. Its outputs and
execution graph come from the framework run.

The website now separates:

- a progressive learning guide;
- a complete exported API reference;
- a 0.2 → 0.3 compatibility and rollout guide.

## Known constraints

- 0.3 is a beta; managed API details may still change before stable.
- Running cancellation/deadlines are cooperative.
- Resident-byte budgets use declared estimates, not browser heap measurement.
- Manifest policy is admission metadata, not a JavaScript sandbox.
- Flows are in-page orchestration, not durable workflows.
- The vision adapter currently keeps `@huggingface/transformers` as a package
  dependency even for applications using only the core APIs. Package splitting
  is a next-release priority.
- Browser/device quality and performance remain application evaluation duties.
